# Audit Logging

## Problem

Agentic systems can make decisions and perform actions autonomously.

For production systems, it is not enough to know that an action happened. You often need to know:

* Who initiated it
* Which agent performed it
* What the agent attempted
* Which tools were used
* What authorization decision was made
* Whether human approval was involved
* What actually happened

This is the purpose of **audit logging**.

---

## Core Idea

Audit logs provide a durable record of security- and business-relevant actions.

```text id="r4m8qx"
User
  │
  ▼
Agent
  │
  ├── Decision
  ├── Tool Request
  ├── Authorization
  ├── Human Approval
  └── Tool Execution
          │
          ▼
      Audit Log
```

Audit logging answers:

> **Who did what, when, against which resource, and what was the result?**

---

## Example: Production Deployment Agent

Suppose an agent deploys version `v2.4.1` to production.

The system should record:

```text id="p8n3vk"
User: user_123
Agent: coding_agent
Action: deploy
Environment: production
Version: v2.4.1
Authorization: allowed
Approval: approved
Approved By: admin_456
Result: success
Timestamp: ...
```

If something goes wrong later, the organization can reconstruct the action.

---

## Audit Event

A structured audit event might look like:

```json id="x3j7qm"
{
  "event_id": "evt_123",
  "timestamp": "2026-09-26T10:30:00Z",
  "request_id": "req_456",
  "user_id": "user_123",
  "agent_id": "coding_agent",
  "action": "deploy",
  "resource": "production",
  "authorization": "allowed",
  "approval": "approved",
  "result": "success"
}
```

Keep audit events structured so they can be searched, analyzed, and correlated.

---

## Audit vs Observability

They are related but serve different purposes.

| Observability                        | Audit                                 |
| ------------------------------------ | ------------------------------------- |
| Debug and understand system behavior | Establish a durable record of actions |
| Performance and reliability          | Security and accountability           |
| Traces, metrics, logs                | Immutable/controlled event records    |
| Engineers are primary consumers      | Security, compliance, operations      |
| Can contain high-volume telemetry    | Focuses on important events           |

For example:

```text id="q6m2vx"
Trace:
"Agent called deploy tool."

Audit:
"user_123 authorized coding_agent
to deploy v2.4.1 to production."
```

## What Should Be Audited?

Important events include:

### Authentication

```text
Login
Token issued
Authentication failure
```

### Authorization

```text
Permission granted
Permission denied
Policy evaluation
```

### Agent Actions

```text
Tool invocation
Agent delegation
Agent-to-agent communication
```

### High-Risk Actions

```text
Data deletion
Financial transaction
Production deployment
Permission changes
External communication
```

### Human Approval

```text
Approval requested
Approved
Rejected
Expired
```

## Audit + Agent Tracing

Audit events should reference the execution trace.

```text id="z5r8kp"
Audit Event
     │
     └── trace_id = abc123
                │
                ▼
           Agent Trace
                │
                ├── LLM
                ├── Tool
                ├── Authorization
                └── Result
```

This gives two levels of visibility:

```text id="v7m3qa"
Audit
→ What important action occurred?

Trace
→ How did the system reach that action?
```

## Audit Integrity

For security-sensitive systems, audit records should be difficult to modify or delete.

Common approaches include:

* Append-only storage
* Restricted write permissions
* Separate audit storage
* Retention policies
* Cryptographic integrity mechanisms
* Access logging for audit records

The exact approach depends on the security and regulatory requirements.

---

## What Not to Log

Never blindly store:

```text id="1w5r8c"
❌ Passwords
❌ API keys
❌ Access tokens
❌ Private keys
❌ Sensitive personal data
❌ Full confidential prompts/responses
```

Prefer:

```text id="v9c2km"
✓ Resource IDs
✓ Request IDs
✓ Action
✓ Status
✓ Actor
✓ Timestamp
✓ Policy decision
✓ Trace ID
```

Use redaction or hashing where appropriate.

---

## Production Considerations

A production audit system should define:

* Event schema
* Required fields
* Retention period
* Access controls
* Data classification
* Redaction rules
* Correlation IDs
* Trace IDs
* Storage durability
* Audit integrity
* Query/search capability
* Alerting for sensitive actions

Audit logs should be generated by the **application/security layer**, not solely by the LLM.

---

## When to Use

Audit logging is essential when agents:

* Access sensitive data
* Modify business records
* Execute privileged tools
* Communicate externally
* Perform financial operations
* Change permissions
* Deploy production systems
* Operate in regulated environments

---

## Trade-offs

| Benefit                 | Cost                      |
| ----------------------- | ------------------------- |
| Accountability          | Storage cost              |
| Security investigation  | Data management           |
| Compliance support      | Privacy considerations    |
| Incident reconstruction | Additional infrastructure |
